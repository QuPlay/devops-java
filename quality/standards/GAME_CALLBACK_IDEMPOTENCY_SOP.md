# 游戏回调幂等与资金安全规范

适用范围：`goplay-game-service` 所有第三方游戏回调(投注/结算/撤单/退款/Jackpot/调账等),以及任何"外部回调驱动钱包账变"的场景。

核心原则:**幂等记录与钱包账变必须落在同一个事务里 —— "记录存在" 必须严格等价于 "账变已成功提交"。** 一旦把二者拆成两个事务,就被迫用状态机(PENDING/DONE)+ 清扫 + 清理器去补偿,且会打开"账变失败却被重试判成功"的刷钱口子。

---

## 1. 红线(违反即阻断合并)

### R1 · 幂等 insert 必须与账变同事务
幂等记录的 `insert` 与 `UPDATE 钱包` 必须在同一 `@Transactional` 内提交。禁止"先在校验阶段独立 insert(自动提交),再另开事务做账变"。
- 唯一键 `(round_id, transaction_id, provider_code, uid)` 即去重器,并发由 DB 唯一键串行化,不依赖分布式锁。
- 失败时事务回滚天然清理,**不需要**清理器/清扫任务/DONE 切面。

### R2 · 禁止删除"已提交"的幂等或账变记录
删除已提交记录 = 对端重试时重新账变 = **反向刷钱**。
- 清理只允许删"未提交"(由事务回滚完成);任何手写 `removeById` 删幂等记录都是高危,审查必须打回。
- 兜底清扫(若有)只删 `created_at` 滞留且确认未发生账变的记录,且必须带状态/条件守卫。

### R3 · 重复请求绝不"谎报成功"
重复回调只有在"记录存在(已提交)"时才返回缓存成功;"在途/未确认"必须返回各厂商可识别的"重试"响应(统一 `CALLBACK_PROCESSING` → `buildInvalidRequest`),**绝不**对未完成的账变返回成功。

### R4 · 扣款 0 行更新不得静默归一为"余额不足"
钱包原子守卫 `UPDATE coin = coin - x WHERE coin >= x` 返回 0 行时必须区分:
- **真实余额 < 需扣** → 归一为 `COIN_INSUFFICIENT`(余额校验后被并发抽走的竞态);
- **投注额 < 余额却 0 行**(余额充足却失败) → 属非余额异常,**预警(log.error)+ 原样上抛**(GlobalExceptionHandler + TG),不得冒认余额不足(否则掩盖真实故障、并可能错误触发对端撤单)。

### R5 · 合并(投注派彩一体)按"投注毛额"校验余额,不按净额
余额=80、投注=100、派彩=70 时,必须按 `80 < 100` 直接拒,**不得**按净额 `80 ≥ (100-70)=30` 放行(否则等于允许用 80 的余额下 100 的注)。毛额闸门放在账变前的余额守卫。

## 2. 正确的幂等模式(参考实现)

```
验证阶段(无事务, 只读):
  existing = SELECT by (round,txn,provider,uid)
  ├─ 命中 → 返缓存成功响应(记录存在 ⟺ 已提交)
  └─ 未命中 → 校验 round/txn 不同时为空 → build 记录(打散 id) → 暂存上下文(不写库)

账变事务内(@Transactional):
  余额毛额守卫(R5) → 原子扣款(R4) → 保存注单 → insert 暂存的幂等记录(写 coin_after)
  catch DuplicateKey(并发同 key) → 抛 CALLBACK_PROCESSING → 回滚(账变一并撤销)
  ── 提交: 钱包 + 注单 + 幂等记录 原子落库 ──
  提交后(doAfterCommitAsync): 刷缓存 + 发 MQ
```

四场景预期:首次→处理一次;重放→缓存成功;失败→回滚无残留可重试;并发同 key→唯一键去重只一次。

## 3. TiDB 写热点(高写表必读)

- **单调聚簇主键(雪花)是写热点** —— 所有插入汇聚单 region。高写表(回调/幂等/流水)的代理主键必须打散:应用侧 `Long.reverse(id) >>> 1`,或 `AUTO_RANDOM`(需建表/重建)。
- 幂等表唯一键含 `uid`(全局),天然隐含租户隔离,无需 `tenant_id` 入键;此类表须在租户拦截器忽略名单中。
- 低基数列(如 `status` 0/1)+ 单调列(`created_at`)的复合索引同样是写热点;清扫类查询优先用"有界时间窗口 + 现成 `created_at` 索引",避免为它专门加单调索引。

## 4. 上线 / 迁移 checklist

- [ ] 并发双花集成测试(真实 MySQL/TiDB, N 线程同 (round,txn) → 钱包只变一次、败者得 `CALLBACK_PROCESSING`)通过
- [ ] 全量回归 `mvn test` 绿 + 人工 code review
- [ ] 逐 provider 核对:`(round_id, transaction_id)` 唯一标识一次资金操作;"纯早返回成功"的 no-op 路径可重放
- [ ] **上线前**对账并清理存量"未提交 PENDING"幂等记录(否则新逻辑会误判为已处理 → 刷钱),DBA 审批
- [ ] 回滚预案就绪;废弃列(如 `status`)的 `DROP COLUMN` 推迟到上线稳定后
- [ ] 上线后观测:`CALLBACK_PROCESSING` 频率、扣款异常预警 TG、各 provider 回调成功率

## 附:背景

源于 2026-06 `goplay-game-service` 幂等"单事务重构":旧设计幂等 insert 与账变分两事务,靠 status(PENDING/DONE)+ 切面 + 清理器 + 清扫 Job 补偿,存在"账变失败却报成功"及"删 DONE 记录→重复账变"两类刷钱风险。重构后塌缩为单事务 + 唯一键,写次数 3→1,上述风险被结构性消除。详见 `goplay-game-service/Readme.md` 回调处理流程一节。
